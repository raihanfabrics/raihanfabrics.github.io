## 1. How to delete wholesale accounts? What if they forget their credentials? *(answered, no code change)*

There is currently **no delete button** for wholesale accounts —
`WholesaleAdmin` / `WholesaleAccountCard` in `src/TextileApp.jsx` only
support **Approve** and **Reject**, nothing that removes a row.

There's also **no self-service "forgot password"** flow. Wholesale buyers
sign in with a phone number + password, which the app maps internally to a
synthetic email address for Supabase's email/password auth (see
`wholesaleEmail()` in `src/lib/supabaseApi.js` and the "Auth note" in
`README.md`). There's no "reset password" link anywhere in that flow.

**What you can do today:** in Supabase mode, both can be handled directly
from the Supabase dashboard (**Authentication → Users** — reset a
password, or delete the user, which you'd pair with manually deleting the
matching row in `wholesale_accounts`). In local mode, wholesale accounts
live in `localStorage` and can only be cleared by clearing browser data or
editing storage directly in dev tools.

**Why it's not just a quick add:** deleting a wholesale account properly
means deleting two things — the `wholesale_accounts` row *and* the linked
`auth.users` row — and the current Row Level Security policy on
`wholesale_accounts` doesn't even have a `delete` policy yet (see
`supabase/schema.sql`). Deleting an `auth.users` row also isn't possible
from the browser with the anon key; it needs the service-role key, which
the app already keeps server-side only (the same reason `embed-fabric`,
`match-fabric`, and `generate-insights` exist as Edge Functions rather
than direct client calls). A real fix would be a small new Edge Function
plus a delete/reset button in the UI — happy to build that as a follow-up
if it'd be useful.

## 2. GPS location for suppliers *(implemented)*

Suppliers can now have a GPS pin captured the same way wholesale buyer
addresses already work: a "Capture current location" button in the
Add/Edit Supplier form (using the browser's Geolocation API), shown
afterward as coordinates plus a "✓" confirmation. In the Suppliers table,
any supplier with a captured location shows an **"Open in Maps"** link
(new **Location** column) instead of relying on the typed address alone.

**Changed:**
- `src/TextileApp.jsx` — `SuppliersAdmin` now captures/displays `lat`/`lng`
  and links out to Google Maps, reusing the existing `.geo-capture` /
  `.geo-confirmed` / `.map-link` styles already used by the wholesale
  signup form.
- `src/lib/localStore.js` and `src/lib/supabaseApi.js` — `addSupplier` /
  `updateSupplier` now accept and persist `lat` / `lng`.
- `supabase/schema_v5_supplier_gps.sql` — **new** migration adding
  `lat`/`lng` columns to the `suppliers` table. Run this in Supabase's SQL
  Editor if you're on Supabase mode (see updated `README.md` setup steps);
  local mode needs no migration.

GPS location is optional per supplier — leaving it blank just means no
"Open in Maps" link shows for that row, same as before.

## 3. Searchable fabric picker in Purchase List's "Add a fabric manually" *(implemented)*

The single long `<select>` dropdown (which lists every SKU) is replaced
with a type-to-search field: type any part of a SKU, color name, or
fabric type, and a dropdown of up to 20 matches appears below the field
(each showing a color swatch, color + fabric type, and SKU). Selecting one
fills the field and enables the **Add** button, same as before. This
should stay usable even once the catalog is in the hundreds of SKUs, since
staff no longer have to scroll a giant list to find one item.

**Changed:** `src/TextileApp.jsx` — `PurchaseList` gained `manualQuery` /
`showSuggestions` state, a `manualSuggestions` filter (plain
`.filter()` over the in-memory product list — fine at this catalog size,
no search index needed), and a new `.manual-suggestions` dropdown with
matching CSS.

## 4. Confirmation before deleting a fabric from Inventory *(implemented)*

Tapping the trash icon in **Inventory** no longer deletes immediately. It
now opens a small centered confirmation dialog ("Delete this fabric?"
naming the specific color/fabric, with **Cancel** and **Delete** buttons)
— nothing is removed until **Delete** is tapped. The same pattern was also
applied to deleting a **Supplier**, since that's an equally easy
accidental-tap target and it made sense to fix both consistently.

**Changed:** `src/TextileApp.jsx` — new reusable `ConfirmDialog` component
(`.confirm-backdrop` / `.confirm-card` / a new `.btn-danger` style),
wired into both `AdminPanel` (Inventory) and `SuppliersAdmin` (Suppliers).
This dialog is generic and can be reused for future destructive actions
(e.g. deleting a wholesale account, if that's built later — see #1).

## 5. Hijri/Shamsi calendar *(answered, no code change)*

There is **no calendar or events feature anywhere in this app** — nothing
to switch to a different date system, because there's no date-based
event/calendar UI to begin with. The closest existing thing is the
**Trends** tab's revenue-by-season view, which uses fixed Gregorian
calendar quarters and is explicitly documented in `README.md` (Roadmap →
Phase 5) as *not* accounting for Hijri/Shamsi dates or moveable events
like Eid or Ramadan — that was called out as a known gap rather than
faked with an approximation that would be wrong most years.

Adding a real Hijri- or Shamsi-aware calendar (e.g. for tracking demand
around specific lunar/solar dates rather than just a labeled season) would
be genuinely new functionality — a date-conversion library, a way to
enter/track events, and a decision about what the calendar should actually
*do* (label historical sales data? project upcoming demand spikes? both?).
Given that scope, it wasn't built as part of this request, but it's a
reasonable Phase to scope out properly if wanted — let me know and I can
put together a concrete plan.

## 6. How does the "Demand" section work? *(answered, no code change)*

It's not missing — it's just fed from a separate tab. In the Admin
sub-navigation:

- **Log Request** (camera icon) is where staff record a fabric a customer
  wanted but the shop couldn't provide — out of stock, never stocked, or
  special order — including an optional swatch photo, quantity, width,
  and the customer's contact info (`CustomerRequestForm` in
  `src/TextileApp.jsx`).
- **Demand** (sparkle icon) is the read-only analytics view built from
  those logged requests: open-request counts, a most-requested list, an
  estimated-lost-revenue figure, and every open request with its photo
  thumbnail, letting staff mark each Fulfilled or Dismiss it.

So the "photo + details" submission you were looking for does exist — it
just happens on **Log Request**, and **Demand** is purely where you read
the results back. This is also already documented in `README.md`'s
Roadmap → Phase 2.
