## 5. "Staff should not be able to edit or delete inventory items"

Fixed in both places that matter:

## 6. Inventory edits not saving, but deletes working for both roles

Two separate bugs, now both fixed:

- **Why edits weren't saving**: `stock_meters` was defined as an
  `integer` column. Fabric stock is measured in meters and is routinely
  fractional (45.5m, 12.25m, etc.) — any edit that saved a non-whole
  number was rejected by the database. Changed the column to `numeric`,
  which allows decimals.
- **Why there was no error message**: on top of that, the save function
  had no error handling at all — if the database rejected the update for
  *any* reason, the form just sat there with no feedback, silently
  discarding the change. Added a proper try/catch with a visible error
  message (same pattern for delete failures too), so if something like
  this happens again you'll see a message instead of a form that looks
  like it did nothing.
- **Why delete worked for both roles when it shouldn't have**: that's the
  same permissions gap as item 5 above — the old policy allowed any
  staff account to delete. Fixed by the same policy change.

## 7. Refresh returning to the home page

The app tracked which page you were on only in memory (React state) —
nothing about it was in the URL, so a refresh always restarted at
"storefront." Added hash-based routing: the URL now updates as you
navigate (e.g. `#/admin/inventory`, `#/matcher`), and on load the app
reads that hash to restore where you were, instead of always defaulting
to the home page. This also plays nicely with the GitHub Pages deploy
above — hash routing needs no server-side URL rewriting rules, which
static hosts like GitHub Pages don't support anyway.

## Applying this to your existing database

You mentioned your database is already set up from the previously
uploaded project. **Do not re-run the full `schema.sql`** — it will error
on the policy names that already exist, and re-insert the seed fabric
rows on top of your real ones.

Instead, open your Supabase project → SQL Editor → New query, paste in
`supabase/migration_2026-07-25.sql`, and run it. It only does two things:

1. Changes `stock_meters` from `integer` to `numeric` (your existing
   stock values are preserved — `12` just becomes `12.0`, nothing is
   lost).
2. Drops the old `fabrics_write_staff_only` policy and replaces it with
   the three narrower ones described in item 5 above.

Nothing else in your database is touched — your fabrics, staff profiles,
wholesale accounts, and every other table/policy/function stay exactly as
they are.
