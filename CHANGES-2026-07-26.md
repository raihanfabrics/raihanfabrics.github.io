# Changes — 2026-07-26

## Shared cart between wholesale buyers

Root cause: the cart is plain in-memory state — nothing tied it to who's
actually logged in, and nothing ever cleared it when the logged-in
account changed. So on the same browser tab: buyer A adds items, logs
out, buyer B logs in — B inherits whatever was still sitting in memory
from A. Fixed: the cart now clears on every wholesale login and logout
(and on staff logout too, for the same reason — staff can browse the
storefront while signed in).

## Record Sale works, but Dashboard/Trends don't reflect it — AND — closing a Market Mode trip says items were added but Inventory doesn't change

These turned out to be **the same root cause**, so one fix covers both.

The Inventory screen (and the Dashboard's low-stock / out-of-stock /
reorder-suggestion numbers) all read from one column:
`fabrics.stock_meters`. But recording a sale and closing a Market Mode
trip both only ever write to `stock_batches` (a separate, more detailed
table that tracks exactly which purchase batch stock came from — that
part was always working correctly). Nothing connected the two: a sale
would correctly reduce `stock_batches.meters_remaining`, but
`fabrics.stock_meters` — the number actually shown on screen — never
moved. A purchase closing a trip had the same gap in reverse.

Local/demo mode never had this problem, because it manually recalculates
and rewrites the displayed stock number after every sale and every
closed trip. Your real Supabase database never got the equivalent.

**Fixed properly, not patched around:** added a database trigger that
keeps `fabrics.stock_meters` permanently equal to the sum of
`meters_remaining` across a fabric's batches, automatically, every time a
batch is created or changes — so this can't drift out of sync again
regardless of which feature touches stock in the future.

One side effect worth knowing: once a fabric has any real purchase/sale
history, its "meters in stock" becomes fully computed from that history.
If you edit that number directly in the Inventory form afterward, it'll
get overwritten the next time a sale or purchase happens for that
fabric. This matches how local/demo mode already worked; fabrics with no
batch history yet (just added by hand) aren't affected until their first
real transaction.

**Action needed:** run `supabase/migration_2026-07-26-stock-sync.sql` —
it adds the trigger AND does a one-time correction of any fabric whose
number is already wrong from testing so far (fabrics with no batch
history at all are left untouched).

## "Clear All" button in Purchase List

Added, next to "Add a fabric manually" — clears every manually-added
item at once (with a confirmation first, matching how deletes work
elsewhere in the app). It only affects manually-added items:
the automatically-suggested ones (low stock, open requests, etc.) are a
live read of current data, not something added, so there's nothing to
"clear" about those — they'll simply stop appearing on their own once
whatever made them low-priority is resolved.
