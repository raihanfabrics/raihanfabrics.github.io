# Changes — 2026-07-27

## ⚠️ Run this migration first
**`supabase/migration_2026-07-27.sql`** — paste it into the Supabase SQL Editor and run it before using the new build. It:
1. Adds an `is_active` column to `fabrics` (for the archive-instead-of-delete fix below) and rebuilds `fabrics_secure` to include it.
2. Adds `fabrics`, `stock_batches`, `sales`, and `sale_items` to the `supabase_realtime` publication (for the auto-refresh fix below).

Both steps are idempotent — safe to run again if you're not sure it already ran.

---

## 1. Record Sale now has a search field, not a dropdown
Each line in Record Sale is now a type-to-search box — type a SKU, color, or fabric type and pick from matches — the same pattern already used in Purchase List's "Add a fabric manually." Picking a fabric still pre-fills the unit price from its retail price like before.

## 2. "Delete this fabric?" no longer crashes with a database error
Deleting a fabric that's ever been sold or purchased was failing with a raw `violates foreign key constraint stock_batches_fabric_id_fkey` error. That foreign key is deliberate — it stops a delete from silently breaking past invoices and the cost trail their profit numbers came from — but the error handling around it wasn't.

Now: a fabric with **no** sale/purchase history still deletes permanently, same as before. A fabric that **does** have history is **archived** instead — it disappears from the storefront, Record Sale, and Purchase List, but stays visible (greyed out) in Inventory with a **Restore** button, and every old invoice still resolves its name correctly. Inventory shows a small note when there are archived items, and a banner confirms which happened right after you confirm a delete.

## 3. "Best-selling fabrics" and "Most profitable fabrics" show names again
Root cause: the Dashboard's data-fetching function was pulling fabric rows straight from the database as raw `fabric_type`/`color_name` fields, but the screen that renders them reads `fabric.colorName`/`fabric.fabricType` — so the name was always blank while the (separately-computed) meters/profit numbers on the right rendered fine.

While in there, also fixed a related bug: "Most profitable fabrics" was being computed by re-sorting the top-8 best-*sellers*-by-volume, which meant a fabric that's very profitable per meter but doesn't move a lot of volume could never appear on that list. It's now computed independently from all fabrics sold.

## 4. Inventory and Dashboard should no longer need a manual refresh
Every action taken *in a given browser tab* already refreshed the right data (Record Sale, closing a Market Mode trip, editing/deleting a fabric). The gap was anything changed *from somewhere else* — another device, another staff login — which that tab had no way to find out about on its own.

Both Inventory and Dashboard now subscribe to Supabase Realtime for the relevant tables and refetch automatically (debounced ~400ms) when something changes anywhere, not just in the current tab. Requires the migration above (adds those tables to the realtime publication) — without it this still works fine for single-tab use, it just won't pick up changes from elsewhere.

## 5. Pashto/Dari translation pass
Went through Dashboard, Trends, Record Sale, Log Customer Request, Demand Intelligence, Suppliers, Purchase List, and Market Mode (trip list, active trip, shopping list rows, add-discovered-item) and wired up every static label, button, table header, placeholder, and message that was still hardcoded English — roughly 150 new translated strings, on top of the ones already done in earlier sessions. Admin screens stay English-only per your standing decision; this covers the customer-facing-adjacent staff tools.

**Known gaps, by design:** the short "reason" phrases Purchase List and Market Mode generate per item (e.g. "out of stock", "42m sold recently") are assembled dynamically and, for Market Mode, get written into the database as plain text on the shopping list item — translating those would mean either storing them pre-translated (locking in whatever language was active when the item was added) or re-deriving them client-side from raw numbers each render. Flagging this rather than guessing — happy to build either approach if it matters enough to be worth it.
