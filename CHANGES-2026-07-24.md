## 1. Wholesale account delete button (owner-only) *(implemented)*

Each wholesale account card (pending, approved, or rejected) now has a
**Delete account** button, visible only to the owner role, with a confirm
dialog before anything happens.

**Why this needed more than a button:** deleting a wholesale account
properly means removing two things — the `wholesale_accounts` row and the
buyer's Supabase Auth login (they authenticate via a synthetic
phone-based email, see `wholesaleEmail()` in `src/lib/supabaseApi.js`).
The second part needs the service-role key, which can't be used from the
browser. This is exactly the gap flagged as unbuilt in last time's
changelog (#1 there).

**Changed:**
- `supabase/functions/delete-wholesale-account/index.ts` — **new** Edge
  Function. Verifies the caller is signed in *and* has the `owner` role
  (checked against `profiles`, using the caller's own session — not
  spoofable), then deletes the `auth.users` row with the service-role
  key. The `wholesale_accounts` row disappears automatically via the
  existing `on delete cascade` foreign key, so no second delete is
  needed.
- `src/lib/api.js`, `src/lib/localStore.js`, `src/lib/supabaseApi.js` —
  new `deleteWholesaleAccount(id)` function in each. Local mode just
  removes the row (no `auth.users` table to worry about there).
- `src/TextileApp.jsx` — `WholesaleAccountCard` gained the Delete button
  (`canManage`-gated, same flag that already gates Approve/Reject) and
  `WholesaleAdmin` gained the confirm-dialog flow, reusing the
  `ConfirmDialog` component built last time for Inventory/Suppliers.
- Deploy step added to `README.md`:
  `supabase functions deploy delete-wholesale-account`.

There's still no self-service "forgot password" flow for wholesale
buyers — that part of last time's answer to this question is unchanged.

## 2. Custom date-range trending in Trends *(implemented)*

A new **Custom date range** section in the Trends tab, sitting alongside
(not replacing) the existing "this month vs last month," "this year vs
last year," and "next week forecast" options. Pick a "From" and "To"
date, and it shows: total revenue, meters sold, sale count, average
revenue/day, and ranked lists of the top-selling fabrics and fabric types
in exactly that window.

This was built as the practical alternative to a real Hijri/Shamsi-aware
calendar (which last time's changelog #5 explained doesn't exist and
would be new scope) — per your note this time, if you know a date like
Eid fell on a particular day last year, you can just type that range in
directly rather than the app needing to know about lunar/solar calendars
at all.

**Changed:** `src/TextileApp.jsx` — `Trends` gained `rangeStart`/
`rangeEnd` state, a `rangeAnalysis` computation (mirrors the existing
season/fixed-comparison logic, just filtered to the picked range instead
of a fixed period), and the new UI section with two date inputs and two
`RankedList`s. New `.date-range-picker` / `.two-col-grid` CSS.

## 3. Form design cleanup *(implemented)*

Every text/number/date/password input, select, and textarea across the
whole app now shares one consistent look — padding, border radius, a
visible focus ring, placeholder/disabled states, and matching checkbox/
file/color-input styling.

**What was actually wrong:** it wasn't that the existing styling looked
bad — `.form-drawer` (Inventory/Suppliers forms) and `.auth-form` (login
screens) were already reasonably styled. The problem was that several
newer screens — **Record Sale**, **Log Request**, and parts of **Market
Mode** — built their own `<label>`/`<input>` markup without either of
those wrapper classes, so their inputs fell back to completely unstyled
browser defaults: thin native borders, inconsistent sizing, no focus
state, fonts that didn't match the rest of the app. That mismatch is
almost certainly what read as "ugly."

**Changed:** `src/TextileApp.jsx` — replaced the three separate,
slightly-duplicated style blocks (`.auth-form label/input`, `.form-drawer
label/input,select`) with one global rule set covering every form control
app-wide by element type rather than by container class, so no screen can
be missed this way again. Also widened `.form-row`'s gap and added a
mobile breakpoint (stacks to one column under 520px instead of squeezing
two fields side by side).

## 4. Suppliers: only the owner can edit or delete *(implemented)*

Any staff can still **add** a new supplier (e.g. logging one they just
found), but only the owner can **edit** or **delete** an existing one —
matching the existing owner-only rule for wholesale accounts.

**Changed:**
- `src/TextileApp.jsx` — `SuppliersAdmin` takes a `canManage` prop; the
  Edit/Delete buttons in the table only render for the owner (staff see
  "Owner only" instead), and the underlying `startEdit`/`requestRemove`
  functions also check the flag directly (defense in depth).
- `supabase/schema_v6_supplier_owner_only.sql` — **new** migration. The
  original `suppliers_staff_only` policy let any staff insert/read/
  update/delete. This replaces it with four policies: any staff can
  still select or insert, but only a `profiles.role = 'owner'` row can
  update or delete. This is the part that actually matters for security
  — the UI hiding the buttons doesn't stop a staff account from calling
  the API directly; the RLS policy does.

## 5. Dashboard + Trends: owner-only *(implemented)*

Both tabs are now owner-only. Staff logins no longer see the **Dashboard**
or **Trends** buttons in the admin sub-navigation at all, and a staff
login now lands on **Inventory** after signing in instead of the
(previously default, now hidden) Dashboard tab.

**Changed:** `src/TextileApp.jsx` — added a general `isOwner` flag
(`adminUser?.role === "owner"`) alongside the existing
`canManageWholesaleAccounts`; both tab buttons are conditionally
rendered, both tab contents are gated with a new `OwnerOnlyNotice`

and `handleStaffLogin` picks the landing tab based on role. **Note:**
unlike Suppliers (#4), this is UI-only — Dashboard and Trends read from
`fetchDashboardMetrics()`, which isn't itself restricted to owners at the
database level, since dashboard/trends data is read-only reporting, not a
row a staff account could damage. If you specifically want staff logins
blocked from *reading* that data too (not just the tab hidden), that
would need an additional RLS-level change — let me know if that's the
intent and I'll add it.

## 6. How are staff accounts added/deleted? *(answered, no code change)*

There's **no in-app UI** for either — same situation wholesale accounts
were in before #1 above. Adding a staff (owner or employee) login is a
manual two-step process, documented at the bottom of `supabase/
schema.sql`: create the Supabase Auth user by hand in the dashboard, then
run one SQL `insert into profiles (...)` giving them a `username`, a
`name`, and a role of `'owner'` or `'staff'`.

There's also **no delete policy on `profiles`** at all yet — removing a
staff login today means deleting their `auth.users` row directly from the
Supabase dashboard (Authentication → Users), same as the wholesale
workaround before #1. In local mode, staff logins are just the
`seedStaffUsers` array in `src/lib/localStore.js` (`owner`/`owner123` and
`staff1`/`staff123` by default) — edited directly in code, not through
any UI, since local mode has no real auth system at all.

If staff turnover is frequent enough that this manual process becomes a
real friction point, that'd be a reasonable small phase to build
properly (a "Staff" admin tab, owner-only, using the same
service-role-Edge-Function pattern as #1) — let me know if that'd help.
